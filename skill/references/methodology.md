# 限额反推方法论

> 详细推导与实测数据，源自本项目对 WorkBuddy 客户端行为与本地日志的联合分析。

## 1. 限额的基本模型

WorkBuddy / CodeBuddy 的限额是 **账号 × 模型** 粒度的**独立配额**：

- 同一个账号下，`hy4-preview` 和 `deepseek-v4.1-flash` 各有各的额度，互不挤占；
- 每个模型各有自己的重置时刻（`next_reset` 各不相同即为此证据）。

这与「账号总池」模式不同——后者不可能出现同一账号下不同模型重置时刻错开的情况。

## 2. 窗口语义：滚动 24 小时

从 429 错误文案中可解析出窗口重置时刻（形如 `将在 2026-10-25 23:00:00 UTC+8 重置`）。

**实测**：把全库所有相邻两次 reset 的间隔算出来，中位数为 **24.01 小时**，与「自然日固定时段重置」明显不符，与「滚动 24 小时窗口」高度吻合。

因此本项目的口径是：

```
窗口 = (now - W, now]，W = 24h（实测中位数 24.01h 取整为 24）
```

**注意**：`limits.json` 中 `thresholds.window_hours_median` 记录的是实测值，不是硬编码的 24。

## 3. 限额反推公式

对某个模型的**每一个** 429 事件：

```
R = 该事件声明的重置时刻
W = 全库观察到的窗口长度中位数
sample = Σ { 该模型在 (R-W, R] 区间内的 credit / token / 请求数 }
```

对该模型的多个样本取**中位数** → 得到该模型的限额估计。

### 为什么是「下界」

被限流这件事本身只蕴含一个信息：**该窗口内的消耗 ≥ 真实限额**。
所以每个样本值都是真实限额的一个**下界**，中位数仍然是下界。

**推论**：任何时候算出 `usage_ratio > 1`，都是**撞 429 的可靠信号**；而 `usage_ratio < 1` 只能说明「按估计还够用」，不能保证一定够。

### 为什么不取全局阈值

全局中位限额（所有模型混在一起算）会**严重失真**：不同模型的限额差异可达数十倍，混算的中位数对任何单个模型都没有参考价值。所以本项目对每个模型**独立反推**。

## 4. 模型归因（难点）

429 的错误行**不带 `model` 字段**——这是反推的第一个障碍。

**会话邻近法**：

1. 把 429 事件按会话分组；
2. 在同会话内，找该 429 **之前 120 秒内最近的一次成功请求**；
3. 该成功请求使用的模型，即为这次 429 的归属模型；
4. 找不到（会话刚开始就 429、或跨会话）时，回退到**该会话内出现次数最多的模型**。

120 秒窗口是经验值：长任务里模型切换通常发生在分钟级，30 秒可能太窄（切模型后的首个请求立刻 429 会被归错），180 秒可能太宽（会串到下一阶段模型）。120 秒在实测中归因准确率最好。

**仍会误判的情况**：同一会话内 120 秒内切换了模型，且切换后立刻触发 429。这种情况占比很低，误差可接受。

## 5. 错误码语义

客户端的业务错误码通过 `lookupBizCode` / `classifyErrorDetail` 归类，完整表见 [error-codes.md](error-codes.md)。

关键区分：

| 类别 | 是否真的「额度不够」 | 处理建议 |
| --- | --- | --- |
| `quota_token_limit` (6004/6000) | ✅ 是 | 换模型 / 等重置 |
| `quota_request_limit` (6005-6008/14003) | ✅ 是 | 降低请求频率 |
| `quota_balance_exhausted` (140xx) | ⚠️ 是余额问题 | 需要充值，**不是**速率限制 |
| `quota_active_session` (10105) | ❌ 并发会话数超限 | 关掉其他会话 |
| `quota_web_search` (15001) | ❌ 只是联网搜索额度 | 关掉联网搜索 |
| `queue_*` (6020-6022) | ❌ 排队，不是限额 | 等待即可 |

> 把 `quota_balance_exhausted` 当成速率限制处理，会得出「等 24 小时就好了」的错误结论。**分类要先做对。**

## 6. 读 SQLite 的坑

`~/.workbuddy/workbuddy.db` 是 WAL 模式的 SQLite。

**直接只读连接会漏数据**——最新写入还在 `-wal` 文件里没 checkpoint。
正确做法：把 `workbuddy.db` + `workbuddy.db-wal` + `workbuddy.db-shm` **三个文件一起复制**到临时目录，再连接临时目录里的副本。读完删临时目录。

本项目已在 `core.read_db_credits()` 中实现这一点。

## 7. 实时额度接口（未打通）

逆向发现客户端渲染层存在以下接口：

| 接口 | 返回 |
| --- | --- |
| `POST /billing/meter/get-user-resource-summary` | `usageTotal` / `usageLeft` / `refreshAt` |
| `POST /billing/meter/get-user-resource-paid-packages` | 付费套餐资源 |
| `POST /billing/meter/get-user-resource-free-packages` | 免费套餐资源 |
| `POST /billing/meter/get-enterprise-user-usage` | 企业版用量 |

**为什么没直接用**：这些接口需要 Bearer Token，而 Token 存放在 Electron 的 **DPAPI 安全存储**中。实测 `~/.codebuddy/` 目录、leveldb 文件、系统 Cookies 均**无明文 JWT**，外部脚本拿不到。

候选解法（见 [roadmap.md](roadmap.md)）：

1. 在渲染层上下文内执行（注入脚本 / DevTools 协议）；
2. 通过 IPC 透传（改动客户端，风险高）；
3. 维持现状：退回日志反推（本项目当前方案）。

## 8. 方法论的可迁移性

这套「**从失败样本反推阈值**」的方法论不限于 WorkBuddy：

> 任何「只有失败时才告知限额」的系统，都可以用「失败事件 + 前置时间窗内的自身消耗」反推阈值。

前提是：失败信息里**携带了阈值相关信息**（本例是重置时刻）。
若不携带，则需要用「重复触发后的间隔」等旁证，精度会显著下降。
