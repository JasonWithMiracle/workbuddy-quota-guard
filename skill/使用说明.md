# WorkBuddy 配额感知器 使用说明

> 版本：1.0.0 ｜ 最后更新：2026-10-25 ｜ 维护者：JasonWithMiracle
> 开源仓库：https://github.com/JasonWithMiracle/workbuddy-quota-guard

---

## 一、功能简介

**一句话**：在 WorkBuddy / CodeBuddy 把你的任务用 429 打断之前，先算出「每个模型还剩多少额度」。

**核心能力**

| 能力 | 说明 |
| --- | --- |
| 限额反推 | 从本地历史 429 事件反推「账号 × 模型」的独立限额（滚动 24h 窗口口径） |
| 实时状态估算 | 按当前滚动窗口统计每个模型自身的消耗，输出已用占比与风险等级 |
| 断点交接 | 一键生成 `handoff.md`，任务被 429 打断时可直接交给下一个模型接手 |
| 可视化看板 | 生成暗色自适应 HTML 看板，浏览器直接打开 |
| Hook 预警 | 会话启动阶段自动检查，高风险模型提前提示 |

**能力边界（必须清楚）**

- ✅ 能做：**估算**剩余额度、**预测**撞 429 风险、**记录**限额规则；
- ❌ 不能做：拿到**实时精确的**剩余额度——客户端登录令牌存放于 Electron DPAPI 加密存储，外部脚本无法读取，本工具只能从日志做**统计下界反推**；
- ❌ 不修改、不删除任何 WorkBuddy 本地数据；
- ❌ 不做任何网络上传。

## 二、适用场景

### 场景 1：任务撞 429 前的额度盘点

> 用户原话：「我现在各模型还剩多少额度？」
> 用户原话：「deepseek 是不是快满了？」

→ 执行 `status`，优先汇报 `risk = high` 的模型。

### 场景 2：任务被 429 打断，需要交接

> 用户原话：「刚被限流中断了，帮我生成一份交接文档给下一个模型。」
> 用户原话：「handoff 文档」

→ 执行 `handoff`，产出五段式 `handoff.md`。

### 场景 3：想看清某个模型的限额规则

> 用户原话：「反推一下各模型的限额表。」

→ 执行 `analyze`，产出 `limits.json`。

### 场景 4：想可视化看整体额度分布

> 用户原话：「做个看板看看。」

→ 执行 `dashboard`，产出 `quota_report.html`。

### 场景 5：会话开始就自动预警（无需主动询问）

→ 配置 `hooks/quota-precheck.js` 到 `~/.workbuddy/settings.json` 的 `SessionStart` 事件。

### ❌ 不适用场景

- 想查**其他账号**或其他机器的额度 → 配额是本账号 × 本机维度，不支持；
- 想知道**账单/扣费明细** → 本工具只看配额限额，不做成本核算（那是 `workbuddy-token-audit` 的职责）；
- 想**实时**精确剩余量 → 做不到，原因见上文能力边界；
- 在**非 WorkBuddy / CodeBuddy** 客户端上使用 → 数据目录结构不匹配。

## 三、调用方式

### 方式 A：作为 Skill 在对话中调用（推荐）

安装到 `~/.workbuddy/skills/workbuddy-quota-guard/` 后，直接用自然语言：

```
查一下我现在各模型还剩多少额度
```

Agent 会加载 `SKILL.md`，按其中的执行流程自动选择子命令并汇报结果。

### 方式 B：直接跑脚本（无需安装 Skill）

```bash
cd <skill目录>
python scripts/quota_guard.py --help
```

### 方式 C：安装为命令行工具（pip）

```bash
pip install -e .
wb-quota-guard status
```

### 最小可用示例（3 步内可用）

```bash
# 1. 进入 Skill 目录
cd ~/.workbuddy/skills/workbuddy-quota-guard

# 2. 看当前状态
python scripts/quota_guard.py status

# 3. 生成交接文档
python scripts/quota_guard.py handoff --out ./handoffs
```

## 四、参数说明

### 4.1 命令行参数

| 参数 / 配置项 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `command`（位置参数） | enum | 是 | — | 子命令：`analyze` / `status` / `handoff` / `dashboard` / `all` / `db` |
| `-o` / `--out` | path | 否 | `./quota-guard-out` | 产物输出目录，不存在会自动创建 |
| `--home` | path | 否 | `~/.workbuddy` | WorkBuddy 数据根目录（用于扫描其他机器/其他 profile 的数据） |
| `--json` | bool | 否 | `false` | `status` 子命令下以 JSON 输出到 stdout，便于脚本消费 |
| `--quiet` | bool | 否 | `false` | 仅输出错误信息，抑制正常回显 |
| `WORKBUDDY_HOME`（环境变量） | path | 否 | — | 等价于 `--home`，优先级：命令行 > 环境变量 > 默认值 |

### 4.2 子命令语义

| 子命令 | 作用 | 产出 |
| --- | --- | --- |
| `analyze` | 扫描日志 → 反推限额规则表 | `limits.json` |
| `status` | 估算当前滚动窗口各模型用量与风险 | `status.json` + 终端表格 |
| `handoff` | 生成 429 断点交接文档 | `handoff.md` |
| `dashboard` | 生成可视化看板 | `quota_report.html` |
| `all` | 依次执行 analyze → status → dashboard → handoff | 以上全部 |
| `db` | 导出会话级 credit 明细（前 20 行） | 终端输出 |

### 4.3 `status.json` 字段说明

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `now` | string | 估算时刻（ISO8601，UTC+8） |
| `window_hours` | float | 滚动窗口长度（实测 ≈ 24.0） |
| `models[].model` | string | 模型名 |
| `models[].total_tokens` | int | 该模型在滚动窗口内的 token 消耗 |
| `models[].credit` | float | 该模型在滚动窗口内的 credit 消耗 |
| `models[].requests` | int | 该模型在滚动窗口内的请求数 |
| `models[].limit_tokens_M` | float/null | 反推的该模型 token 限额（单位 M），样本不足时为 `null` |
| `models[].usage_ratio` | float/null | 已用占比，`> 1` 表示已超估计限额 |
| `models[].risk` | string | 风险等级：`low` / `medium` / `high` |
| `models[].next_reset` | string | 下次窗口重置时刻，未知则为 `"未知"` |
| `models[].hits_429` | int | 该模型历史 429 触发次数 |

## 六、注意事项与已知限制

### 前置依赖

- Python **3.9+**，**零第三方依赖**（纯标准库）；
- 可读写 `~/.workbuddy/` 下的会话日志与数据库（只读访问）；
- 若要读 `workbuddy.db`，脚本会自动把 `db` + `-wal` + `-shm` 一起复制到临时目录再连接（**必须如此**，否则会漏掉 WAL 中的数据）。

### 权限 / 风控

- ✅ 全程**只读**，不修改、不删除 WorkBuddy 任何数据；
- ✅ **不联网**，不上传任何数据；
- ⚠️ 生成产物含本机统计信息（模型名、token 量、429 次数），**不要**提交到公开仓库或贴到公开场合；
- ⚠️ 产物默认写在 `--out` 目录，**不要**写进用户的知识库仓库（会污染 Obsidian 索引）。

### 已知限制

| 限制 | 说明 |
| --- | --- |
| ⚠️ 限额是**统计下界** | 由「触发 429 时的窗口内消耗」取中位数得到，只会**低估**真实限额。`usage_ratio > 100%` 属常态 |
| ⚠️ 样本少的模型不可信 | 如某模型仅 3 次触发，其限额估计误差大，需实际触发后校准 |
| ⚠️ **拿不到真实剩余额度** | 客户端令牌存于 Electron DPAPI 安全存储，外部脚本读不到。逆向发现的 `POST /billing/meter/get-user-resource-summary` 接口需在渲染层内调用 |
| ⚠️ 依赖本地日志 | 清理会话日志会导致历史限额样本丢失，需重新积累 |
| ⚠️ 平台相关 | 仅适配 WorkBuddy / CodeBuddy 桌面客户端的数据目录结构 |
| ⚠️ 窗口语义假设 | 假设为滚动 24h 窗口（实测中位数 24.01h）；若上游改为自然日配额，本工具需相应调整 `current_status()` 的窗口口径 |

### 常见问题

**Q1：为什么 `usage_ratio` 显示 175%，不是超 100% 吗？**
A：这是正常现象。限额是**下界估计**（被限流只说明「至少」消耗到超限），所以真实限额往往高于估计值。`usage_ratio > 1` 的正确解读是「**已超历史估算限额，撞 429 风险高**」。

**Q2：`next_reset` 显示「未知」是 bug 吗？**
A：不是。该模型的历史 429 事件没有携带可解析的重置时刻，或该模型在窗口内从未触发过 429，属信息缺失，如实标注为「未知」。

**Q3：跑一次要多久？**
A：扫描量取决于会话日志规模。本机 702 个会话文件 / 57,392 条请求，一次完整 `all` 约需 10–20 秒。日常只想看状态时，用 `status` 即可。

**Q4：清理了 WorkBuddy 会话历史，还能用吗？**
A：能跑，但 `limits.json` 中的限额样本会退化（`samples` 趋近 0），此时 `limit_*` 返回 `null`、`usage_ratio` 为 `null`，属预期行为。

**Q5：能给出精确的剩余额度吗？**
A：不能，原因见「已知限制」。本工具的价值在于**提前预警 + 规划建议**，而非精确读数。
