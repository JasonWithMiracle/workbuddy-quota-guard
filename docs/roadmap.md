## v1.1 —— 精度校准 ✅ **已交付（v1.1.0）**

**问题**：当前限额是统计下界，样本少的模型误差大。

**已实现**：

- [x] **社区校准数据池**：开放接受社区提交的实测样本
- [x] **样本格式**：JSON Schema 定义（`calibration/schema/sample.schema.json`）
- [x] **采纳规则**：≥2 个独立贡献者 + 相对离散度 ≤25% + 剔除少数派离群者
- [x] **置信度字段**：`status.json` 新增 `limit_source` 与 `confidence`
- [x] **参考限额表**：随版本分发，`status` 自动加载并优先于本机反推值
- [x] **月度发布工作流**：每月 1 日自动检查，有变更才发版
- [x] **单元测试**：29 个用例

**仍待补齐**：

- [ ] **离群值过滤（窗口维度）**：当前只过滤了「贡献者之间」的离群，
      尚未剔除「单个 429 事件窗口内混入其他模型消耗」的样本
- [ ] **多窗口交叉验证**：同时用 12h / 24h / 48h 窗口反推，取一致性最好的 W
- [ ] **人工锚点录入 UI/CLI**：`calibrate sample` 目前只生成自动反推样本，
      人工锚点需手改 JSON，可考虑增加交互式录入
- [ ] **精度评测集**：构造 ≥10 个模型的带真值样本集，作为回归基准

**验收标准（部分达成）**：与人工校准值的相对误差 < 15% —— 需等社区样本积累到
足够规模后方可量化验证。

## v1.2 —— 打通实时额度接口

**问题**：拿不到真实剩余额度（客户端令牌在 Electron DPAPI 安全存储）。

候选路径（按可行性排序）：

| 方案 | 描述 | 风险 |
| --- | --- | --- |
| A. 渲染层内执行 | 在客户端渲染进程上下文中调用 `POST /billing/meter/get-user-resource-summary`，返回 `usageTotal` / `usageLeft` / `refreshAt` | 低（只读，不改客户端） |
| B. IPC 透传 | 走客户端已有的 IPC 通道取额度 | 中（依赖客户端内部协议，版本升级易碎） |
| C. 维持日志反推 | 当前方案 | 无，但精度受限 |

- [ ] 验证方案 A 的可注入性
- [ ] 实现实时额度 + 估算值**双通道**，并给出置信度标注

**注意**：任何方案都不得提取或落盘客户端登录令牌。

## 贡献指引

最欢迎的贡献类型：

1. **实测校准数据**：某 WorkBuddy 版本 / 某模型的限额实测值 —— 直接提交
   `calibration/samples/` 下的样本文件即可，指南见 [`calibration/README.md`](../calibration/README.md)；
2. **CodeBuddy CLI 适配**（v1.3）；
3. **实时额度接口方案**（v1.2）；
4. **其他平台适配**：任何「只在失败时才告知限额」的系统，都可以用本仓库的方法论反推阈值。

### 校准数据的采纳门槛

样本进入随版本分发的参考表，需满足：

- 同一模型同一窗口下 **≥2 个独立贡献者**（同一人的多条样本会折叠为一条）；
- 剔除少数派离群者后，各维度相对离散度 **≤25%**；
- 人工锚点（已知确切消耗时触发 429）权重为自动反推的 **3 倍**，但同样需要交叉验证。

未达标的样本会落入 `conflicts` 区标注分歧原因，不会被丢弃，也不影响其他人使用。
